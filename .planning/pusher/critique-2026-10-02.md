# Critique — 2026-10-02 (v0.5.189)

Baseline: 927 tests / 50 suites pass, `npx tsc --noEmit` clean (after `npm install`
in a fresh worktree; `jest-expo/web` is not resolvable without it).

## What is genuinely good

- **Pure-helper discipline.** Screen logic that matters (`stage.ts`, `progress-stats.ts`,
  `food-partition.ts`, `cascade-delete.ts`, `merge-foods.ts`, `export.ts`) is extracted and
  unit-tested. `cascade-delete.ts` and `merge-foods.ts` take a narrow structural DB interface,
  so they are testable without drizzle.
- **The migration is executed in a test** against `node:sqlite` (`src/db/__tests__/migration.test.ts`),
  including query-plan assertions that name the expected index. Few RN apps do this.
- **Mutation-checked tests.** The changelog shows tests being deleted when they passed with the
  code removed. That discipline is rare and is why the suite can be trusted.
- **Privacy-conscious telemetry**: Sentry screenshots off and query params redacted
  (`src/lib/sentry.ts`).

## Top 3 things that will hurt in six months

### 1. There is no schema-migration path — only `CREATE ... IF NOT EXISTS`
`src/db/migration.ts` has no `PRAGMA user_version` and no `ALTER TABLE`. The next column
added to `src/db/schema.ts` (and the Convex sync plan needs at least `synced_at` to start
being written, probably `updated_at`/`deleted_at` too) will exist on fresh installs and
**be missing on every existing install**; drizzle will then emit SQL naming a column that
is not there and every read of that table fails. CLAUDE.md already notes that all CHECK
constraints from v0.5.123–131 are "forward-only", which is this same problem in a milder form.

Related: `PRAGMA foreign_keys` is never turned on (`src/db/client.ts:5`), so every
`REFERENCES` clause in `migration.ts:27-80` is decorative. That is why the cascades are
hand-written in `cascade-delete.ts`; it also means an orphan exposure can be inserted at any time.

**Recommendation:** add a versioned migration runner now (read `user_version`, apply
numbered steps, bump it), before the first column change forces one under pressure. Decide
explicitly whether to enable `foreign_keys` (and test it in `migration.test.ts`).

### 2. Data access is inlined in screens, and `app/food/[id].tsx` has grown into a 1,397-line god component
- 30 inline `db.select/insert/update/delete` calls across 8 screen files (12 in `app/food/[id].tsx` alone).
  The stated next priority — Convex sync with SQLite fallback — will need to touch every one of them.
  There is no repository/data layer to swap.
- `app/food/[id].tsx:48-93` holds **20 `useState` slots and 9 separate in-flight latches**, and
  ~15 handlers (`handleBumpStage`, `handleDeleteExposure`, `handleSelectExposureStage/Rating`,
  `handleSaveNotes/Date`, `handleMergeInto`, `handleSaveName`, `handleSelectCategory/Preparation`,
  `handleDeleteFood`, …) that each repeat the same latch → try → `db.update` → patch local state →
  `console.error` + `Alert.alert` → finally-release shape. The v0.5.174 refactor collapsed the
  four per-exposure editors; the food-level editors (name, category, prep, safe-food) still have one
  latch and one or two booleans each.
- The consistency rule is already slipping: `handleToggleSafeFood` (`app/food/[id].tsx:446`) is the
  one write handler with no latch, contrary to the CLAUDE.md "Writes are latch-guarded" convention.
  (Harmless today because the write is idempotent per closure, but it shows the rule is enforced by
  memory, not structure.)

**Recommendation:** introduce `src/data/` with per-entity functions (`foods.rename`,
`exposures.updateField`, …) behind the same structural-interface trick `cascade-delete.ts`
already uses, plus a small `useGuardedWrite(label, fn)` hook that owns latch + catch + Alert.
Split `food/[id].tsx` into `FoodHeaderEditor` and `ExposureHistory` components. Do this
*before* Convex, so sync becomes a change to `src/data/`, not to 8 screens.

### 3. The documentation has become the bottleneck, and it contradicts itself
- `CLAUDE.md` is **423 KB** (~190 changelog entries, many 400+ words). It is loaded into every
  agent session's context; most of it is history that `git log` already holds. `NEXT_STEPS.md`
  is another 45 KB and opens by warning that its own "Recently shipped" list is stale.
- Every commit must hand-edit the version in `src/lib/constants.ts` (176 commits touch it — the
  most-changed source file in the repo) plus the test count in ~4 places in CLAUDE.md.
- Direct contradictions:
  - CLAUDE.md "Next Priority" says wire Convex (`fetchChildren` → `addFood` → `logFood`);
    `NEXT_STEPS.md` "Do Not" says **"Do not wire Convex. Revisit later."**
  - `NEXT_STEPS.md` claimed "Join flow works". It cannot work across devices:
    `app/onboarding/join.tsx:45` looks the code up in the *local* SQLite DB, and the code generated in
    `app/onboarding/index.tsx:26` is never displayed by any screen. README line 21 implies the code is
    meaningful. **Fixed the NEXT_STEPS line in this session** (doc-only).

**Recommendation:** move the changelog to `CHANGELOG.md` (or let commit messages carry it) and
cap CLAUDE.md at conventions + current state, well under 20 KB. Pick one of the two Convex
directives and delete the other. Either hide the Join Family entry point until sync exists, or
label it "same device only".

## Smaller observations

- `food_chains` is created, cascaded and merged (`cascade-delete.ts`, `merge-foods.ts`) but nothing
  ever inserts a row. It's dead weight that every destructive path has to maintain.
- `convex/` mirrors the schema by hand (`convex/schema.ts`) with no check that it stays in step with
  `src/db/schema.ts`; it has already drifted conceptually (unauthenticated — see security-2026-09-27.md).
- The test harness's `createMockDb` does not evaluate `where` predicates (noted in v0.5.183), so
  family-scoping on reads is held by inspection only. A `node:sqlite`-backed drizzle instance (the
  migration test already has one) would make those guards testable.
