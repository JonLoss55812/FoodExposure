# Critique — 2026-10-23 (v0.5.226 → v0.5.227)

Baseline: 1043 tests / 67 suites pass, `npx tsc --noEmit` clean (after `npm install`;
a fresh worktree has no `node_modules`). After this session: same counts, still clean.

This review follows `critique-2026-10-02.md` (v0.5.189). Its point #1 (no migration
path) was fixed well: v0.5.190 added a versioned runner and v0.5.193 turned on foreign
keys, with real-SQL tests. Its points #2 and #3 are unchanged or worse. They come up
again below, with new evidence.

## What is genuinely good

- **Real-SQL testing.** `src/test-utils/sqlite-db.ts` gives drizzle over `node:sqlite`
  with the shipped migrations and FKs on. Family scoping, cascades and the
  `occurred_at`-in-seconds bug (v0.5.199) are now tested against real rows instead of
  a fake that ignores `where`. This is the best thing added since the last critique.
- **Migration runner** (`src/db/migrate.ts`). It uses one transaction per step,
  `user_version`, rollback on failure and leaves a downgraded database alone. Each
  behaviour is mutation-tested.
- **Mutation discipline.** Almost every changelog entry says which deletion fails which
  test. That is why a green suite here means something.
- **Pure helpers** (`stage.ts`, `progress-stats.ts`, `exposure-order.ts`,
  `merge-foods.ts`, `export.ts`) keep the logic that matters testable without rendering.

## Fixed this session (the one allowed fix)

**Join Family sent every joiner back to the welcome screen.** `app/onboarding/join.tsx`
called `login()` but never `setOnboarded(true)`. `app/(tabs)/index.tsx:115-118` replaces
to `/onboarding` whenever `isOnboarded` is false, and since v0.5.80 `logout()` resets it.
So a parent who joined, on a fresh install or after Sign Out, ended up on the welcome
screen while signed in. One "Get Started" tap from there creates a *new* family and logs
them into it, abandoning the family they joined.

The join test's happy path asserted `isAuthenticated`/`familyId`/`displayName` but not
`isOnboarded`, so 13 green tests never saw this. Fixed in v0.5.227 (`e961faf`): the new
assertion was red first, and removing the call fails it again.

This is how the next three findings show up in practice. The suite tests each screen
alone, but no test follows a flow across screens, and the app has never been run.

## Top 3 things that will hurt in six months

### 1. The app has never run anywhere, and the suite cannot show that it would

- `ios/`/`android/` do not exist, `app.json:52` and `eas.json:24-26` still hold
  `YOUR_*` placeholders, and CLAUDE.md records "Not device-verified" / "no native build"
  8 times for changes that matter on device: crypto source (v0.5.180), FK pragma
  (v0.5.193), the migration runner (v0.5.190) and the error boundaries (v0.5.186/189).
- Web is not a fallback either. CLAUDE.md's Known Limitations says expo-sqlite probably
  cannot open, because the HTML document is served without COOP/COEP.
- The bug fixed above lasted from v0.5.80 to v0.5.226, about 146 versions. It was
  invisible to tests that render one screen with mocked navigation, and visible within
  ten seconds of a real run. v0.5.180 (`uuid` throwing on Hermes, so **every insert**
  would have failed) was the same kind of bug. It was found by reading code, not by
  running the app.

**Recommendation:** get one dev-client build running (`npx expo run:ios` or
`run:android` locally, no EAS account needed). Walk through onboarding → add child →
add food → log → export by hand. Then add one cross-screen flow test that keeps the real
stores and walks create-family → add-child → dashboard and join → dashboard. Before any
more hardening, find out whether the flows work at all.

### 2. Family isolation is patched screen by screen instead of at its source

Of 65 commits since 2026-10-02, 11 fix "data isolation". Examples: v0.5.195 food detail,
v0.5.197 export, v0.5.200 Log form, v0.5.201 Progress, v0.5.202 bump, v0.5.219 tab
layout, v0.5.226 export helper. Each one defends against a persisted `selectedChildId`
that names another family's child. There are still more readers without the defence:
`app/(tabs)/foods.tsx:61-67` and `app/food/[id].tsx:123-141` read exposures by
`selectedChildId` alone, and `app/(tabs)/index.tsx:57` relies on `ensureSelection` having
run first.

The state can arise in two ways:
- `app/onboarding/_layout.tsx` has **no authenticated guard**, and `app.json:6` registers
  the `tonguetutor` scheme. A deep link to `/onboarding/join` or `/onboarding` while
  signed in calls `login()` (`src/stores/auth-store.ts:59`), which swaps `familyId` and
  leaves `selectedChildId` untouched. `onboarding/index.tsx` would also create a second
  family over a live session.
- MMKV partial corruption, where the auth store resets but the child store survives.

Sign Out (`settings.tsx:204`) already clears the selection, so the realistic route is
the deep link, and nothing tests it.

**Recommendation:** close it in two places instead of eleven.
- Have the child store remember the `familyId` its selection belongs to, and treat a
  mismatch as no selection. Alternatively, have `login()` callers clear the selection.
- Add a guard to the onboarding layout that redirects an authenticated, onboarded user
  to the tabs.

Keep the per-query family predicates as defence in depth, but stop adding new ones one
version at a time.

### 3. The project's memory costs more than the code, and the code's hot spot keeps growing

- `CLAUDE.md` is **465 KB**, up from 423 KB at the last critique. 449 KB of it is
  changelog. It is roughly 115k tokens, loaded into every agent session. `NEXT_STEPS.md`
  grew from 45 KB to **69 KB** across 36 sections and still opens by warning that its own
  list is stale.
- Since 2026-10-02, the most-changed files are `CLAUDE.md` (41 commits),
  `src/lib/constants.ts` (38, only for `APP_VERSION`) and `NEXT_STEPS.md` (19). Then come
  `app/food/[id].tsx` and its test (10 each).
- The Convex contradiction from the last critique is still there. CLAUDE.md "Next
  Priority" says to wire Convex; `NEXT_STEPS.md:1047` says "Do not wire Convex".
  `NEXT_STEPS.md:686` acknowledges this and leaves it alone.
- `app/food/[id].tsx` is **1,456 lines** (1,397 at the last critique), with 18
  `useState`, 9 latches (lines 94-105), 21 `Alert.alert` calls and 11 inline `db.*`
  calls. Each handler repeats latch → try → write → patch → log + alert → release.
  v0.5.206 and v0.5.207 were both stale-closure races between these handlers, which is
  the cost of this shape showing up as bugs.

**Recommendation:**
- Move the changelog to `CHANGELOG.md` and keep CLAUDE.md to conventions plus current
  state, under 20 KB.
- Collapse NEXT_STEPS to a single current gap list.
- Delete one of the two Convex directives.
- For `food/[id].tsx`, extract a `useGuardedWrite(label, fn)` hook (latch, catch, alert,
  release) and split out `FoodHeaderEditor` and `ExposureHistory`. The screen tests in
  `app/food/__tests__/id.test.tsx` are a good safety net for the split.

## Smaller observations

- `convex/` (8 files) is still unreferenced and unauthenticated
  (`security-2026-09-27.md`), and `food_chains` is still never inserted. Both are dead
  weight that `cascade-delete.ts`, `merge-foods.ts` and the schema still have to
  maintain.
- Several screens destructure the whole child store (`const { selectedChildId } =
  useChildStore()`), so they re-render on any store change. This is harmless at this
  size. `src/stores/child-store.ts:74` already exports a selector hook that nothing uses
  consistently.
- A pusher worktree needs a ~1 min `npm install` before anything runs. NEXT_STEPS already
  notes this.
