## What is genuinely good

- **The isolation fix is the right shape.** One invariant lives in one store
  (`auth-store.ts:50-56`), so screens no longer each have to remember it. That is the
  difference between eleven patches and one.
- **Store hydration is defensive in the right place.** `auth-store.ts:92-100` refuses an
  `isAuthenticated: true` blob whose identity tuple is incomplete. `child-store.ts:62-70`
  type-checks the persisted selection. Corrupt MMKV degrades to "signed out" instead of
  crashing.
- **The DB boot path is careful.** `src/providers/DatabaseProvider.tsx:26-44` makes
  migrations single-flight, so StrictMode's double effect cannot re-apply a step. It
  turns on FKs *after* the migrations, with the reason written down, and shows a Retry
  instead of a dead end.
- **The docs are now usable.** NEXT_STEPS is a real open-items list with "how to maintain
  it" rules, and CLAUDE.md fits in context.
- **Mutation discipline is still applied to every test commit**, and each CHANGELOG entry
  names the mutations it catches.

## Fixed this session (the one allowed fix)

**Nothing stopped a new hard-coded colour.** v0.5.153–v0.5.156 removed the last hex
literals, and `contrast.test.ts` checks the theme tokens, but no test checked that
screens *use* tokens. The per-screen theme tests added in v0.5.249–v0.5.263 catch a
literal only on the specific elements they pin.

v0.5.264 adds `src/styles/__tests__/no-colour-literals.test.ts`. It copies the shape of
`placeholder-color.test.ts` and scans every non-test `.tsx` under `app/` and `src/` for a
quoted `'#hex'`, `'rgb('` or `'rgba('`. Mutation check: adding `'#FF0000'` to
`src/components/Button.tsx` fails that file's case. Adding `'rgba(0,0,0,1)'` to
`app/food/[id].tsx` fails that file's case. Both were reverted. The full suite and tsc
are green.

## Top 3 things that will hurt in six months

### 1. The session loop has moved to safe work while the real risks stay open

Since 2026-10-23 there have been 59 commits. 28 of them are theme or colour work: the C9
per-screen light/dark tests, v0.5.249–v0.5.263. Another 19 are docs, mostly
"update NEXT_STEPS after …". **None** touch NEXT_STEPS B1 (run the app) or C1 (the
`food/[id]` hook). Both were named as the top risks three weeks ago.

The C9 tests mostly restate the stylesheet. In `app/child/__tests__/id.test.tsx` (v0.5.263),
for example, the test asserts that the title is `colors.text` and the age is
`colors.textSecondary`. That catches a token *swap*, which is a design choice, not a bug.
Every future restyle has to edit these tests as well. NEXT_STEPS C9 has itself grown
into a 25-line paragraph on jsdom colour quirks (`NEXT_STEPS.md:104-128`). That is
knowledge about the test harness, not about the product. The failure mode that matters,
a hard-coded colour that ignores dark mode, is now covered across the whole codebase by
the 30-line scan above.

**Why it hurts:** every pusher session ends green and adds tests, so the project *looks*
healthy. Meanwhile the one fact that would invalidate a lot of that work, whether the app
boots on a device, stays unknown. v0.5.180 (`uuid` throwing on Hermes, so every insert
would fail) and the v0.5.227 join bug were both visible within seconds of a real run.

**Recommendation:**
- Close C9. Every screen and component now has a theme test, and the source scan covers
  the rest. Delete the C9 paragraph from NEXT_STEPS.
- Have the next pusher session that has a machine with Xcode or an Android SDK run
  `npx expo run:android` (no EAS account needed). It should walk onboarding → add child
  → add food → log → export and record what it sees.
- If no session can run a native build, say that plainly in NEXT_STEPS. Then stop
  scheduling "hardening" and "tests" tasks whose value depends on it.

### 2. `app/food/[id].tsx` is the one file every change has to go through, and it keeps growing

- `app/food/[id].tsx`: 1,472 lines. Latches at lines 94-105 (ten of them). Handlers from
  `handleBumpStage` (:159) to `handleDeleteFood` (:682), with 11 inline drizzle calls
  (:124, :182, :230, :281, :335, :398, :463, :486, :602, :637, :668).
- Its test, `app/food/__tests__/id.test.tsx`, is **2,024 lines**. It runs against a FIFO
  queue of canned reads (`createMockDb`), so adding one read to `loadData` reorders the
  queue for every test. NEXT_STEPS C5 already declined a correctness fix (hiding Bump for
  a foreign child) for exactly this reason (v0.5.203).
- It is the most-changed screen in the project's history (42 commits; only CLAUDE.md, `constants.ts` and NEXT_STEPS change more). Two
  past bugs (v0.5.206/v0.5.207) were stale-closure races between its handlers.

**Why it hurts:** the test harness's shape now discourages fixes. Once a screen is too
expensive to change, fixes get written down instead of made, and C5 is that already
happening.

**Recommendation:** do C1 as its own session. Extract `useGuardedWrite`, keeping the four
release behaviours NEXT_STEPS C1 lists. Then split out `ExposureHistory` (the row editors,
:270-480) and `FoodHeaderEditor` (rename/category/prep/safe, :482-680). Each piece gets
its own test file with its own short read queue.

### 3. The stated next priority (sync) cannot be built on this schema or this data access

CLAUDE.md "Next Priority" says to wire Convex, keeping SQLite as a fallback. The code is
not ready for that in three concrete ways:

- **No change tracking.** Every table has `synced_at` (`src/db/schema.ts:8,18,29,41,59,69`)
  but no `updated_at`. An exposure edited after sync (stage, rating, notes or date are all
  editable in `food/[id].tsx:270-480`) has nothing that marks it dirty, so `synced_at`
  alone cannot tell a sync loop what to push.
- **Hard deletes, with no tombstones.** `src/lib/cascade-delete.ts:35-53` and
  `merge-foods.ts:117` `DELETE` rows outright. A second device can never learn that a
  child or food was deleted, so it will re-upload it.
- **No data-access seam.** Screens call drizzle directly: 29 call sites across 8 files in
  `app/` (`food/[id]` 11, `(tabs)/index` 4, `log`/`join`/`onboarding/index` 3 each,
  `progress`/`foods` 2, `food/add` 1). Moving any entity to Convex, or dual-writing it,
  means editing every screen that touches it, and rebuilding the queued-read mocks in
  their tests.

Separately, the multi-statement writes (the cascades and `mergeFoods`) run without a
transaction. `cascade-delete.ts:21-25` argues that dependents-first order leaves a
retryable state, and for a single device that is acceptable. Under sync, a half-applied
delete becomes a half-synced delete.

**Recommendation:** a human should first resolve NEXT_STEPS A1 (sync: yes or no). If yes,
the first PR should not be "wire `fetchChildren`". It should be:
1. A migration step that adds `updated_at` and `deleted_at`, plus a write path that sets them.
2. A small repository module per entity (`src/data/exposures.ts`, …) that screens call
   instead of `db`. Mock that module in tests, not the drizzle builder.

If no, delete `convex/`, the `synced_at` columns' future-sync comments, and CLAUDE.md's
"Next Priority" section. Nobody should have to maintain an unused backend.

## Smaller observations

- **NEXT_STEPS C numbering skips 3 and 4** (C1, C2, C5…). That suggests items were deleted
  without renumbering. Harmless, but cross-references like "C9" in commit messages will
  drift if anyone renumbers later.
- **Some guards defend against rows the schema already forbids, with long history
  comments.** `src/lib/progress-stats.ts:66-76` is an 11-line comment for a `rating` range
  check that the v0.5.82 `CHECK` constraint already enforces on fresh installs. The guard
  is cheap. The comments, which read like changelog entries ("Same drift class as
  v0.5.106…"), are not: 61 `v0.5.NNN` references in non-test source. The CHANGELOG is
  the place for them.
- **`package-lock.json` is gitignored** (NEXT_STEPS C11). That has already caused one
  breakage (unistyles 3.8 requiring RN 0.85, v0.5.248). This is a policy call, but the
  case for committing a lockfile gets stronger with each such incident.
- **`food_chains` is still never inserted**, but `cascade-delete.ts` and `merge-foods.ts`
  still maintain it. This is the same point as the last two critiques.
