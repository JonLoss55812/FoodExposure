# Critique — TongueTutor (FoodExposure)

Date: 2026-09-01 · Branch: `pusher/work-1788318002` · Reviewer: automated pass
Baseline: **615 tests / 32 suites, all passing**; `npx tsc --noEmit` clean.

---

## What is genuinely good

This is not a codebase in trouble, and it deserves to be said plainly before
the criticism.

- **`src/lib/` is excellent.** `in-flight.ts`, `cascade-delete.ts`, `stage.ts`,
  `progress-stats.ts`, `food-partition.ts`, `thresholds.ts` are small, pure,
  well-named, and carry docstrings that explain *why* rather than *what*.
  `src/lib/in-flight.ts:1-23` is a model comment: it names the exact failure
  the abstraction exists to prevent (a `useState` guard read from a stale
  render closure) instead of restating the code.
- **`CascadeDeleteDb` (`src/lib/cascade-delete.ts:12-16`) is a good seam** — a
  structural interface narrow enough to fake in a test and wide enough that the
  real drizzle instance satisfies it without a cast. That is the right way to
  make DB code testable without a DI framework.
- **The reasoning about ordering is correct and documented.** The
  dependents-first delete order and the `or(sourceFoodId, targetFoodId)` sweep
  (`cascade-delete.ts:34-38`) are subtle and would have been easy to get wrong.
- **TypeScript is genuinely strict and genuinely clean.** `strict: true`, no
  `any` escape hatches left in the screens, and `tsc --noEmit` passes.
- **The domain research is real.** `research-food-exposure-methods.md` and the
  15/20/30 threshold model in `thresholds.ts` mean the app is grounded in
  something, not invented. That is rarer than good code.

## The three things that will hurt most in six months

### 1. There is no migration system, and the schema is defined four times

**Evidence:**

| Definition | File | Status |
|---|---|---|
| Runtime DDL (what actually creates tables) | `src/providers/DatabaseProvider.tsx:13-83` | authoritative |
| Drizzle types (what the query builder checks against) | `src/db/schema.ts` | types only |
| SQL migration file | `src/db/migrations/0000_init.sql` | **dead — never executed, already drifted** |
| Convex backend | `convex/schema.ts` | unused |

`grep -rn "0000_init"` returns exactly one hit: `drizzle.config.ts:5`, the
config that *generates* it. Nothing reads it. It has already drifted — the live
DDL carries `CHECK(length(invite_code) = 6)`, `CHECK(rating BETWEEN 1 AND 5)`,
`CHECK(created_at > 0)` and six more constraints that `0000_init.sql` does not.
A contributor who reasonably assumes the `migrations/` directory is the source
of truth will be reading a file that has been wrong for dozens of commits.

The deeper problem is `CREATE TABLE IF NOT EXISTS`. That statement is a no-op
on any device that has already launched the app. **There is no path to change
the schema for an existing install.** The changelog acknowledges this seven
times — "forward-only protection", "existing installs keep the old schema"
(v0.5.123, v0.5.125, v0.5.126, v0.5.127, v0.5.130, v0.5.131) — but each entry
treats it as an accepted limitation rather than a blocker. It is a blocker.
The moment v1.0 ships to a real device, adding one column requires writing a
migration runner *and* backfilling installs that were created without it.

Six-month cost: every schema change becomes a research project. The planned
Convex sync (CLAUDE.md "Next Priority") will need `synced_at` semantics and
almost certainly new columns; that work will stall on this.

**Recommendation.** Before shipping, introduce a `user_version`-based migration
runner in `DatabaseProvider` (expo-sqlite exposes `PRAGMA user_version`; ~30
lines), move the DDL out of the component into `src/db/migrations/`, and either
adopt `drizzle-kit generate` properly or delete `drizzle.config.ts` and
`0000_init.sql` so there is exactly one schema of record.

### 2. "100% coverage" was measured over a denominator that excluded the product

**Evidence:** `jest.config.js` previously listed `collectCoverageFrom: ['src/**/*.{ts,tsx}', ...]`
with no `app/` entry. Every screen — all the DB access, every write handler,
every `Alert` branch — was outside the measurement. Measured honestly:

```
src/components  100%      app/(tabs)/index.tsx      0%   (lines 28-254)
src/lib         100%      app/(tabs)/foods.tsx      0%   (lines 23-221)
src/stores      100%      app/(tabs)/log.tsx        0%   (lines 22-395)
src/db          100%      app/(tabs)/progress.tsx   0%   (lines 17-253)
                          app/food/add.tsx          0%   (lines 20-206)
                          app/child/add.tsx         0%   (lines 17-169)
                          app/onboarding/add-child  0%   (lines 17-180)
                          app/onboarding/index.tsx  0%   (lines 13-116)
All files: 60.44% lines
```

`app/(tabs)/log.tsx` — creating an exposure, *the core action of the product* —
is entirely uncovered. Three screens have tests (`join`, `food/[id]`,
`settings`); seven do not.

This is not merely a reporting gap; it explains where the effort went. Consider
`src/lib/validation.ts`: 113 lines of schema backed by a **1074-line** test
file. Three of its six schemas have zero production callers:

```
loginSchema:      0 non-test references  (21 in validation.test.ts)
registerSchema:   0 non-test references  (15 in validation.test.ts)
joinFamilySchema: 0 non-test references  (27 in validation.test.ts)
```

`joinFamilySchema` is the sharpest case. `app/onboarding/join.tsx:26-40`
deliberately bypasses it and re-implements validation inline with ad-hoc
`Alert` calls. So the join flow has two validators: a heavily-tested one that
never runs, and an untested one that does. The changelog is candid about this
("this screen bypasses the schema", v0.5.76; "the schema is the contract for
any future ingest path", v0.5.103) — but a contract with no counterparty is
just a test suite testing itself.

Six-month cost: the suite grows, confidence grows, and neither tracks risk. A
regression in `log.tsx`'s submit handler ships green.

**Fixed in this session (one line, verified):** `app/**/*.tsx` added to
`collectCoverageFrom`. Reported coverage moved 100% → 60.44%; 615 tests still
pass. The number got worse because it got true.

**Recommendation.** The `createMockDb` harness (`src/test-utils/mock-db.ts`,
v0.5.146) already works and is proven on three screens — it is the single best
piece of leverage in the repo. Point it at `log.tsx` next. Then delete
`loginSchema`/`registerSchema`/`joinFamilySchema` and their ~63 test
references, or wire `joinFamilySchema` into `join.tsx` so the tests defend
something real. Do not keep both.

### 3. CLAUDE.md — the file loaded into every session — describes a different app

CLAUDE.md is the most-changed file in the repository (147 commits, vs. 135 for
the runner-up). It is also substantially wrong above the changelog. Verified
claims:

| CLAUDE.md says | Reality |
|---|---|
| `src/hooks/` — Custom hooks (useFood, useChild, …) | Directory does not exist |
| "Key Hooks: `useChild()`, `useFood(id)`, `useFoods()`, `useLog()`, `useProgress()`" | `grep` returns **zero** matches for any of them |
| "Next Priority → step 4: Update `src/hooks/useChild.ts`" | File does not exist; instructs the next session to edit fiction |
| "Allergen Tracking: Mark known allergies and aversions" (Key Features) | `grep -ri allergen src app convex` → **zero hits** |
| Schema: `foods (…, allergen_flags)`, `logs (…)` | No `allergen_flags` column; the table is `exposures`, not `logs` |
| "Convention: Allergen flags stored comma-separated" | Nothing to store |
| `tests/` directory at repo root | Tests are colocated in `__tests__/` |
| `convex/functions.ts` | Six separate files; no `functions.ts` |
| "130+ tests, 6 suites, 43.8% line coverage" | 615 tests, 32 suites |
| "Current state: stable (1.0.0)" | `APP_VERSION = 'v0.5.148'` |
| `app/(tabs)/index.tsx (Foods — main list)` | It is the dashboard; `foods.tsx` is the food list |
| "`bun run eas:build:ios`" | No such script in `package.json` |

Meanwhile the parts that *are* accurate — the 250-line changelog — carry a
level of detail (individual test names, mutation-verification notes, rejected
alternatives) that belongs in commit messages, where it already is. The file is
now ~120 lines of stale guidance followed by ~250 lines of append-only log,
and it is the first thing any contributor or agent reads.

Six-month cost: this is self-reinforcing. Each session reads the stale header,
trusts it, and appends another changelog entry — which is exactly the pattern
the last 148 versions show. The header has not been corrected once in 147
commits.

**Recommendation.** Two edits, both cheap. (a) Delete or correct every row in
the table above — the hooks section, the allergen feature, the schema block,
the test counts, the `eas:build` scripts. (b) Move the changelog to
`CHANGELOG.md` and keep CLAUDE.md to conventions + current version. The
changelog is good work; it is just in the file that gets loaded into every
context window.

## Smaller observations

- **No linter, no CI, no typecheck script.** `package.json` has 7 scripts, none
  of which is `typecheck` or `lint`. There is no `.github/`, no eslint config,
  no pre-commit hook. Every changelog entry ends "TypeScript clean" — that is a
  human remembering to run `npx tsc --noEmit`, 148 times. One
  `"typecheck": "tsc --noEmit"` script and a three-line GitHub Actions workflow
  would make it structural instead of heroic.
- **Cascade deletes are not transactional.** `deleteFoodCascade`
  (`cascade-delete.ts:29-40`) issues three sequential awaited deletes. The
  ordering makes a mid-sequence failure *retryable*, which is a real
  improvement over the alternative — but it still means a failure after step 2
  has permanently destroyed every exposure for that food while the food row
  survives. That is unrecoverable user data. `expo-sqlite` supports
  `withTransactionAsync`; wrapping both cascades is a small change with a large
  payoff.
- **Convex is ~200 lines of unreferenced scaffolding.** `convex/*.ts` is
  excluded from `tsconfig.json`, ignored by `testPathIgnorePatterns`, and
  imported by nothing. `ConvexProvider.tsx:5` still points at
  `https://placeholder.convex.cloud` and is mounted in `app/_layout.tsx`.
  Harmless today, but it is unchecked code that will be assumed to work when
  sync begins.
- **Duplicated chip rows.** The same ~28-line `Controller` + `Pressable.map`
  block appears four times in `app/(tabs)/log.tsx` (lines 239, 269, 299, 330)
  and again in `app/food/add.tsx:161`, with close variants in `settings.tsx`
  and `foods.tsx`. The cost is already documented: v0.5.137 had to fix one
  deselect bug in **six places at once**, and could not test any of them
  because the markup is inline. A `<ChipRow options label value onChange />`
  component would collapse ~180 lines and become testable like `RatingPicker`
  already is.
- **No data-access layer.** 24 raw `db.select/insert/update/delete` calls are
  spread across 10 screen files (`app/food/[id].tsx` alone has 5). Combined
  with the missing `src/hooks/` that CLAUDE.md promises, this is the single
  biggest reason screens are hard to test — and the reason the Convex
  migration will touch every screen instead of one module.
- **Minor query inefficiency.** `app/(tabs)/index.tsx:59-64` does
  `db.select().from(exposures)` and uses only `.length` — a full row fetch to
  produce a count. Irrelevant at MVP scale; worth a `count()` when convenient.

## Honest summary

The engineering *discipline* here is high — the defensive-guard work, the
mutation-verified tests, the changelog rigour are all above average. The
problem is that the discipline has been aimed at the safest 40% of the
codebase. Roughly 150 of the 615 tests defend pure helpers against
hypothetical non-string inputs from ingest paths that do not exist, while the
form that creates an exposure has never been rendered in a test.

The three findings above share one root: **effort has followed what is easy to
verify rather than what is likely to break.** Pure functions are easy, so they
got 100% coverage and a dozen typeof guards. Screens are hard, so they got
zero. Schema migration is hard, so it got a `CREATE TABLE IF NOT EXISTS` and
an acknowledgement in the changelog. CLAUDE.md's header is nobody's job, so it
has been wrong for 147 commits.

The good news is that the hard parts are now unblocked. `createMockDb` exists
and works. The lib layer is clean enough that a data-access module would be
straightforward. Correcting CLAUDE.md is an afternoon. If the next few
sessions go to `log.tsx` coverage, a migration runner, and the CLAUDE.md
header — instead of the 149th defensive typeof guard — this is a healthy
codebase.
